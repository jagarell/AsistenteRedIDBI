Two full plan-mode passes were used given the size (first for Home/drawer/Perfil/Configuración, a second re-entry when the user sent the rest of the screens — re-entering plan mode mid-session when scope expands is the right call, not barreling ahead on an already-approved plan).

## Batch 1 — Home / navigation drawer / Mi Perfil / Configuración

- **Navigation drawer**: `activity_main.xml` wrapped in a hand-rolled `DrawerLayout` (not `NavigationView` — no built-in pinned-footer support) + new `view_nav_drawer.xml`. `SessionViewModel` (already Activity-scoped, already drove login/home routing) extended with `loadDrawerProfile()`/`logout()`/`DrawerProfile` instead of adding a second ViewModel — reuses the existing `navigateToLogin()` popUpTo logic in `MainActivity` for free. `AssistantHomeViewModel`'s own `logout()` (added earlier in the session as a stopgap PopupMenu) was removed once the drawer replaced it.
- **Mi Perfil**: rebuilt from a near-empty stub (avatar+name+email+logout button) into avatar+role+company, 3 real stat tiles (`ProfileStats.evaluationsThisMonth` did exist, wasn't fake), "Información Personal" card, and an edit mode that turned out to reuse `PerfilViewModel.startEditing()`/`draftFullName` etc. — already fully built in the ViewModel, just never wired to any UI.
- **Configuración**: built from near-scratch (was previously just a static "Versión 1.0.0" text). New `ConfiguracionViewModel` + new `AppPreferences` (DataStore) for the 4 toggle switches — explicitly local-only, no backend endpoint exists for them, never fakes a server round-trip.

## Batch 2 — everything else

- **Auth screens** (Login/Registro/Recuperar/Nueva Contraseña): added leading icons to every field (new `ic_email`/`ic_person`/`ic_phone` vectors; reused `ic_lock_outline`/`ic_building`/`ic_account_circle`). Login's "Recordar sesión" checkbox already existed in `LoginViewModel` (`rememberMe`/`onToggleRememberMe()`) but was `visibility="invisible"` in XML — just needed wiring, not building. **Recuperar Contraseña deliberately keeps its real "código" copy** instead of the Figma's "enlace" wording — the real flow issues a 6-digit code (email delivery still gated behind `MAIL_ENABLED`), there is no real link-based reset, and changing the copy to promise a link would be dishonest UI.
- **Historial**: was showing 5 hardcoded fake restaurants in `HistorialFragment.kt` while a fully-built, correct `HistorialViewModel` (real `ListEvaluationsUseCase`) sat unused. Reconnected for real. Also fixed the "+" FAB, which passed a literal string `"new"` as `evaluationId` — now calls `StartEvaluationUseCase` for a real evaluation, same as Home's card.
- **Evidencias**: confirmed byte-for-byte already matching the Figma (2-col grid, icon/title/subtitle/pill) — zero changes. User explicitly required the dynamic checklist data flow (`EvidenceViewModel`/`EvidenceAdapter`/`toDisplayItem()`) stay untouched regardless of visual work; it already looked right so there was nothing to reconcile.
- **Chat**: added a real "✎ Editar respuesta" feature (didn't exist before) under each sent user answer. The chat engine is stateless per-request (`answer` endpoint takes the full answers map + the answer for `currentStep`), so "edit" = client-side truncate to the target step's stored `(stepIndex, inputType, options, answersSnapshot)` — captured on every `ChatMessage` at creation time — then let the existing render/submit path re-run. No backend change needed. `"Ir a Evidencias"` link visibility was deliberately left as-is (only appears at full completion) rather than matched to the Figma's earlier appearance, since Evidencias' checklist seeds from chat answers and showing the link mid-chat risks an incomplete seed.
- **Equipment price seam** (3 repos, additive, `null` today): `idbi-fastapi/app/chat/schemas.py::EquipmentRecommendation.unitPrice` → gateway `EquipmentRecommendation.java`/`ProposalPdfRequest.EquipmentLineDto` → Android `TechnicalEquipmentRecommendation`/`TechnicalEquipmentRecommendationDto`/`EquipmentLineDto`. Same "prepared but off" pattern as `OPENAI_API_KEY`/`RUC_VALIDATION_*`: no IDBI price catalog exists anywhere, so nothing is fabricated; it just flows through as `null`/absent until a real catalog is wired into `proposal.py`.
- **New PDF preview screen** (`PdfPreviewFragment`/`fragment_pdf_preview.xml`): didn't exist before (PDFs opened via an external-viewer `Intent`). Renders the *real* generated PDF's actual pages via `android.graphics.pdf.PdfRenderer` into a `ViewPager2` (new `androidx.viewpager2` dependency) — deliberately not a fabricated "summary card" like the Figma mockup shows, since the real PDFBox-generated PDF is plain text and doesn't look like that; rendering the real bytes was chosen over inventing matching visual content. ## Post-redesign polish round (same session, after user screenshots of the running app)

- **Status bar was purple, not blue** — global theme gap: `Base.Theme.AsistenteRedIDBI` never set `android:statusBarColor`, so Material3's default (purple-ish, since `colorPrimary` was never customized) showed through on every screen. Fixed once in `themes.xml` (`android:statusBarColor="@color/header_blue"` + `windowLightStatusBar=false`), not per-screen.
- **Login header/scroll bug**: header was 280dp tall but the ScrollView's `layout_marginTop` was only 230dp — a 50dp gap where the two were supposed to line up. At rest this just looked like a (semi-intentional-looking) card overlap; once the card was scrolled it created a visibly broken seam. Fixed by shrinking the header to 200dp and the margin to 180dp, and generally compacting the login card (padding 26dp→20dp, several 18-24dp gaps→10-16dp) — compacting also made the screen fit in the viewport without scrolling at all on a typical device, which incidentally eliminated the whole bug class rather than just patching the numbers.
- **Two icon drawables were 3x oversized**: `ic_lock_outline.xml` and `ic_lock_reset.xml` both declared `android:width="64dp" android:height="64dp"` with a `viewportWidth/Height="24"` — i.e. a real, larger-than-intended intrinsic size baked into the file (not a viewBox scale issue). Every OTHER icon in the app is declared at 24dp/24. Since `app:startIconDrawable` on a `TextInputLayout` has no explicit size attribute, it renders at the drawable's own intrinsic size, so these two rendered ~3x bigger than sibling icons in the same field row. Swept the whole `drawable/ic_*.xml` set for the same mismatch (`grep` intrinsic width vs viewport) — nothing else was wrong. **Cheap check when a specific icon "looks too big" next to same-sized siblings: compare its declared `android:width`/`height` to its `viewportWidth`/`Height`, not just the drawable itself.**
- **Custom checkbox vs. AppCompat auto-tinting**: needed a Figma-exact checkbox (gray-outline empty square unchecked, solid blue + white checkmark checked) — built as a `layer-list`/shape selector (`selector_checkbox.xml`) applied via `android:button` on a real `<CheckBox>`. AppCompat's `CompoundButton` support auto-applies the theme's `colorControlActivated` (here: Material3's default purple, since never customized) as a tint *on top of* any custom `android:button` drawable — even `app:buttonTint="@null"` didn't reliably suppress it (checked state rendered as a solid purple square with the white checkmark invisible, blended into the same-hue background). Root cause is CompoundButton's tinting mechanism, not the drawable. **Fix that actually worked: stop using `<CheckBox>` entirely — plain `<View>` + manual `setBackgroundResource(checked ? stateCheckedDrawable : uncheckedDrawable)` in the Fragment, toggled on click, state driven by the ViewModel like everything else.** More reliable than fighting CompoundButton tinting for any custom multi-state checkbox look in this app going forward.
