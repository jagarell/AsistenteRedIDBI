Confirmed 2026-09-15, a second and distinct cause of "app can't reach the gateway" beyond [gateway-port-conflict-voya](project_gateway_port_conflict.md): the user has **Proxyman** running on the Mac, configured as the system-wide web proxy on every network interface (`127.0.0.1:9090`), and it also injects `HTTP_PROXY`/`HTTPS_PROXY` env vars into the shell profile. The Android emulator, per its own docs, auto-detects a proxy from the *launching shell's* `http_proxy` env var when `-http-proxy` isn't passed explicitly — so any emulator launched from a shell with Proxyman's env vars set inherits that proxy and routes all app traffic (including `10.0.2.2:8080` → the local gateway) through it.

**Symptoms were much messier than the port-conflict case** — not a clean instant 403, but intermittent: some requests hung 30s and timed out, others got `SocketTimeoutException`, others got `java.io.IOException: unexpected end of stream` mid-response. This cost a lot of back-and-forth (tried `adb shell settings put global http_proxy :0`, a plain `adb reboot`, a full `emu kill`+relaunch, even briefly `killall Proxyman` — reopened immediately per explicit user instruction, since it broke other things the user had open) before finding the actual fix.

**The fix that worked**: relaunch the emulator from a shell with those env vars explicitly unset — `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy ~/Library/Android/sdk/emulator/emulator -avd <name>` — without touching Proxyman itself, since quitting it was explicitly not wanted (it's the user's active tool for other work).

**Why this matters:** raw TCP tests from inside the guest (`nc`) also failed even after clearing the guest's own `settings put global http_proxy :0`, which is what pointed at a *host-launch-environment* cause rather than an in-guest Android setting — worth remembering as a diagnostic shortcut: if `adb shell settings put global http_proxy :0` doesn't fix it, check the *launching shell's* env (`env | grep -i proxy`), not just the guest.

**How to apply:** before debugging "app can't reach gateway from emulator" as a code/backend problem, check both known environmental causes in order: (1) `lsof -i :8080` for a squatting process (Voya), (2) `env | grep -i proxy` in the shell that launched (or will launch) the emulator, and relaunch with `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy` if any are set. Never quit Proxyman (or any user tool) to test this without asking first — it's actively used for other work.

**Recurred 2026-09-15, new trigger:** after switching Android's `BASE_URL` from the local loopback (`10.0.2.2:8080`) to the real Railway domain (`https://asistenteredidbi.up.railway.app`), OkHttp Profiler showed `Unable to resolve host ... No address associated with hostname` on every request — the OLD symptom (hangs/`SocketTimeoutException`) didn't recur; this time it was clean DNS failure. Root cause: `10.0.2.2` is a numeric emulator-to-host alias that never needs DNS resolution at all, so the exact same broken-proxy-inherited-at-launch condition had been silently present the whole session without ever manifesting — it only surfaces once the app needs to resolve a *real* external hostname. Diagnostic tell: `adb shell ping -c 2 8.8.8.8` succeeds (raw IP, ICMP) while `adb shell ping <any real hostname, even google.com>` fails with "unknown host" — confirms guest-level DNS is broken, not just one hostname. Fix was identical to before: `adb -s emulator-5554 emu kill` (needed a follow-up `kill -9 <qemu pid>` from `ps aux | grep qemu-system` once, since `emu kill` reported OK but the process lingered in state `UN`), then relaunch via `nohup env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy ~/Library/Android/sdk/emulator/emulator -avd Android_30 &`. Confirmed fixed via `adb shell ping -c 2 <the real target hostname>` resolving before reinstalling/relaunching the app — don't declare it fixed on `8.8.8.8` alone, that only proves raw connectivity, not DNS.
